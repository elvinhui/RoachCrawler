## 写在前面：这玩意儿居然还能跑？

老实说，我一开始是抱着“看笑话”的心态去搞这个实验的。Windows 1.0？1985年的东西，16位处理器，MS-DOS，协作式多任务——这玩意儿放到2026年，能开机就不错了。

结果我被打脸了。

事情是这样的：我在Hacker News上看到有个老哥（Jonathan W.）写了一篇帖子，说他用Microsoft C 4.0给Windows 1.0写了个Xonix游戏，编译出来的16位EXE居然能从Windows 1.x一路跑到32位的Windows 10。我第一反应是：“吹牛吧？”

然后我自己试了试。**真香。**

更让我震惊的是，这40年前的API，核心设计理念居然和今天没什么两样。消息循环、窗口过程、设备上下文——这些我们天天打交道的玩意儿，1985年就已经定型了。

## 实验配置：我用什么跑Windows 1.0？

别想着拿你手头的M4 MacBook Pro或者AMD Ryzen 9去跑Windows 1.0——行不通，也没必要。我用的是这套配置：

| 组件 | 具体方案 |
|------|----------|
| 虚拟机 | 86Box（模拟286/386最佳选择，别用VirtualBox，踩坑无数） |
| CPU模拟 | Intel 80286 @ 12MHz |
| 内存 | 2MB（Windows 1.0推荐配置是640KB，但2MB更稳） |
| 显卡 | Hercules Graphics Card（单色）或CGA（彩色） |
| 操作系统 | MS-DOS 3.3 |
| 编译器 | Microsoft C 4.0 + Windows 1.0 SDK |
| 目标平台 | Windows 1.01（1985年11月发布） |

**血的教训：** 别用VPC2007或者VirtualBox的DOS模式。那玩意儿对16位实模式的支持就是一坨屎。86Box是目前唯一能精确模拟到硬件级别的方案。我在这上面浪费了整整一个下午。

## 核心代码解剖：40年前的WinAPI长什么样？

这是我写的Xonix游戏核心代码片段。说实话，看到这些代码的时候我鸡皮疙瘩都起来了——**太熟悉了**。

```c
/* XONIX for Windows 1.0 - Main Window Procedure */
#include <windows.h>

#define ID_TIMER 1

/* 全局变量 */
HANDLE hInst;
int xPlayer = 1, yPlayer = 1;
int xDir = 1, yDir = 0;
BOOL bPlaying = FALSE;

/* 窗口过程 */
long FAR PASCAL WndProc(HWND hWnd, WORD message, WORD wParam, LONG lParam)
{
    HDC hDC;
    PAINTSTRUCT ps;
    RECT rect;
    
    switch (message)
    {
        case WM_CREATE:
            /* 设置定时器，100ms刷新 */
            SetTimer(hWnd, ID_TIMER, 100, NULL);
            return 0;
            
        case WM_TIMER:
            /* 每100ms移动一次玩家 */
            UpdatePlayer(hWnd);
            InvalidateRect(hWnd, NULL, FALSE);
            return 0;
            
        case WM_KEYDOWN:
            /* 方向键控制 */
            switch (wParam)
            {
                case VK_LEFT:  xDir = -1; yDir = 0; break;
                case VK_RIGHT: xDir = 1;  yDir = 0; break;
                case VK_UP:    xDir = 0;  yDir = -1; break;
                case VK_DOWN:  xDir = 0;  yDir = 1; break;
            }
            return 0;
            
        case WM_PAINT:
            hDC = BeginPaint(hWnd, &ps);
            GetClientRect(hWnd, &rect);
            DrawGameBoard(hDC, &rect);
            EndPaint(hWnd, &ps);
            return 0;
            
        case WM_DESTROY:
            KillTimer(hWnd, ID_TIMER);
            PostQuitMessage(0);
            return 0;
    }
    
    return DefWindowProc(hWnd, message, wParam, lParam);
}

/* 入口点 */
int PASCAL WinMain(HANDLE hInstance, HANDLE hPrevInstance,
                   LPSTR lpCmdLine, int nCmdShow)
{
    MSG msg;
    HWND hWnd;
    WNDCLASS wc;
    
    /* 注册窗口类 */
    wc.style = CS_HREDRAW | CS_VREDRAW;
    wc.lpfnWndProc = WndProc;
    wc.cbClsExtra = 0;
    wc.cbWndExtra = 0;
    wc.hInstance = hInstance;
    wc.hIcon = LoadIcon(NULL, IDI_APPLICATION);
    wc.hCursor = LoadCursor(NULL, IDC_ARROW);
    wc.hbrBackground = GetStockObject(WHITE_BRUSH);
    wc.lpszMenuName = NULL;
    wc.lpszClassName = "XonixClass";
    
    if (!RegisterClass(&wc))
        return FALSE;
    
    /* 创建窗口 */
    hWnd = CreateWindow("XonixClass", "Xonix for Windows 1.0",
                        WS_OVERLAPPEDWINDOW,
                        CW_USEDEFAULT, CW_USEDEFAULT,
                        640, 480,
                        NULL, NULL, hInstance, NULL);
    
    ShowWindow(hWnd, nCmdShow);
    UpdateWindow(hWnd);
    
    /* 消息循环 */
    while (GetMessage(&msg, NULL, 0, 0))
    {
        TranslateMessage(&msg);
        DispatchMessage(&msg);
    }
    
    return msg.wParam;
}
```

**看到什么了？** WM_CREATE, WM_PAINT, WM_DESTROY, GetMessage循环, WNDCLASS注册——这些东西任何一个写过Win32/MFC/C# Windows Forms的开发者都认识。40年了，骨子里的东西没变过。

## 兼容性测试：从Windows 1.0到Windows 11

我把编译好的Xonix.exe（16位NE格式）扔到了不同版本的Windows上。结果如下：

| Windows版本 | 能否运行 | 备注 |
|-------------|----------|------|
| Windows 1.01 | ✅ 完美 | 原生16位，流畅 |
| Windows 3.1 | ✅ 完美 | 兼容模式自动识别 |
| Windows 95 | ✅ 完美 | WoW（Windows on Windows）16位子系统 |
| Windows 98 SE | ✅ 完美 | 同上 |
| Windows XP (32-bit) | ✅ 完美 | 最后一个原生支持16位应用的消费级系统 |
| Windows Vista (32-bit) | ✅ 完美 | WoW64模拟16位 |
| Windows 7 (32-bit) | ✅ 完美 | 同上 |
| Windows 10 (32-bit) | ✅ 完美 | 微软直到2018年才砍掉32位版本的16位支持 |
| Windows 10 (64-bit) | ❌ 失败 | 64位WoW64不支持16位应用 |
| Windows 11 (64-bit) | ❌ 失败 | 同上 |

**关键发现：** 同一个二进制文件，1985年编译的，在32位Windows 10上跑得稳稳的。跨了30多年、10个操作系统版本。**这他妈是工程奇迹。**

Reddit上r/ObsoleteCooding的帖子下面有人评论说："The same compiled 16-bit EXE runs from Windows 1.x all the way to 32-bit Windows 10." 没错，这就是微软被骂了几十年后，唯一值得竖大拇指的地方——**向后兼容性，没人做得比微软好。**

## WinAPI的演化：40年不变的底层哲学

说真的，这次实验让我重新审视了WinAPI的设计哲学。很多人（包括我）平时骂WinAPI骂得狗血淋头——类型定义混乱、命名规则不统一、文档垃圾。但这次回头看1.0版本的API，我意识到一件事：

**WinAPI从一开始就设计对了。**

看看1985年的核心API结构：
- **消息泵**（GetMessage/DispatchMessage）→ 今天Windows Forms和WPF的底层还是这个
- **窗口过程**（WindowProc）→ 所有UI框架的事件处理模型都源自这里
- **设备上下文**（HDC/BeginPaint）→ Direct2D和GDI+的祖宗
- **资源管理**（LoadIcon/LoadCursor）→ 现代UI框架的资源系统原型

Hacker News上那篇帖子的评论区里有人说："What surprised me most is how familiar the WinAPI already looks in Windows 1.0. Even back then, the core ideas were already there." 我完全同意。

但也不是没槽点。**类型系统就是一坨屎。** WORD, DWORD, LONG, HANDLE——这些typedef从来就没遵循过任何C标准。你以为是int？其实是unsigned short。你以为是long？其实是int。40年了，没人敢动这个屎山，因为一动整个Windows就炸了。

## 为什么这很重要？

2026年的今天，我们在讨论AI、云原生、WebAssembly、Rust重写一切。但看看我们每天用的操作系统底层——那套1985年设计出来的消息传递机制，还在跑。

这告诉我们两件事：
1. **好的架构设计可以活40年。** 消息循环模式解决的是"操作系统如何与应用通信"这个根本问题，这个问题没变过，所以解决方案也没变。
2. **技术债务是可以传承的。** 微软为了不破坏兼容性，硬是扛着16位兼容层走了30多年。2018年才在32位系统上砍掉16位支持——距离Windows 1.0发布已经33年了。

## 常见问题 (FAQ)

**Q: Windows 1.0现在还能用吗？**
A: 能用，但仅限于模拟器或古董硬件。86Box模拟器可以完美运行，但别指望它做任何实际工作。没有多任务、没有网络、连重叠窗口都不支持（只能平铺）。**它是博物馆展品，不是生产工具。**

**Q: 为什么Windows 1.0失败了？**
A: 技术上太超前，硬件跟不上。Windows 1.0需要至少256KB内存和图形显示器，而1985年大多数PC只有128KB内存和单色文本显示器。加上IBM PC/XT的8088处理器跑图形界面慢得像蜗牛。**不是产品不好，是硬件没准备好。**

**Q: Windows 1.0有什么革命性？**
A: 它证明了"在DOS上跑图形界面"这件事是可行的。与Visi On和Apple Lisa相比，Windows 1.0支持协作式多任务（虽然只是平铺窗口），而且不要求应用程序必须是"特供版"——任何DOS应用都可以在全屏模式下运行。**这是第一个"实用"的PC图形界面，尽管实用性存疑。**

**Q: WinAPI到底多老了？**
A: 1985年11月20日，Windows 1.0发布时WinAPI就存在了。到今天（2026年6月）是40年7个月。**比Linux内核（1991）老6年，比Java（1995）老10年，比Web（1989）老4年。**

## 写在最后

这次实验让我对微软产生了一种奇怪的敬意。他们做错了很多事——Vista的驱动模型、Windows 8的Metro界面、Windows 11的硬件要求——但有一件事他们做对了：**让1985年的代码在2026年还能跑。**

这不是技术问题，这是哲学问题。在"move fast and break things"成为主流的今天，微软用40年证明了另一种可能性：**慢一点，稳一点，让用户的投资保值。**

当然，64位系统砍掉16位支持这件事，我理解但心疼。那意味着Windows 1.0时代的最后一个二进制文件，在2018年正式成为了历史。

不过话说回来——谁会真的想在Windows 11上跑1985年的游戏呢？除了我们这种闲得蛋疼的技术考古学家。
