## What You're Actually Seeing

`psql: error: connection to server at "192.168.1.100", port 5432 failed: Connection refused`

Or the slightly more cryptic:

`Is the server running on that host and accepting TCP/IP connections?`

I've hit this more times than I care to admit. Last month our internal analytics tool went dark—monitoring went red across the board, all `connection refused`. First thought: PostgreSQL crashed. But `systemctl status postgresql` showed it was running fine. That's when things got interesting.

## Root Cause: Who's Actually Refusing the Connection?

Here's the thing most people get wrong: "Connection refused" isn't PostgreSQL being picky. It's a TCP-level rejection. Your client sent a `SYN` packet, and the target machine either:

1. Has no process listening on that port
2. Has a process listening, but not on that IP/port combination
3. Has a firewall silently dropping or actively rejecting the packet

The key insight? `pg_hba.conf` has nothing to do with this error. That file only gets read **after** the TCP handshake completes. If you're getting "connection refused", the auth config isn't even in the picture yet.

## Step-by-Step: Follow This Order, Don't Skip

### Step 1: Is PostgreSQL Actually Running?

```bash
# Quick process check
ps aux | grep postgres

# Systemd approach
systemctl status postgresql

# The real test—check the port
ss -tlnp | grep 5432
```

No `postgres` process on 5432? Check the logs:

```bash
journalctl -u postgresql -n 50 --no-pager
```

Common culprits I've seen: disk full (PostgreSQL refuses to start), shared memory misconfiguration, corrupt WAL files.

### Step 2: What's PostgreSQL Listening On?

This is the number one gotcha. Out of the box, PostgreSQL **only listens on localhost**. If you want remote connections, you must change `postgresql.conf`.

```bash
# Find your config file
psql -U postgres -c "SHOW config_file;"

# Or brute-force find it
find /etc/postgresql -name "postgresql.conf"
```

Edit this parameter:

```ini
# Listen on all interfaces
listen_addresses = '*'

# Or specific IPs
listen_addresses = 'localhost,192.168.1.100'
```

Restart and verify:

```bash
systemctl restart postgresql
ss -tlnp | grep 5432
```

You should see:

```
LISTEN 0  244  0.0.0.0:5432  0.0.0.0:*
```

### Step 3: pg_hba.conf—Order Matters More Than You Think

Don't just set everything to `trust`. That's how breaches happen. Be surgical:

```bash
# Allow specific subnet
host    all             all             192.168.1.0/24          md5

# Allow all (really think about this)
host    all             all             0.0.0.0/0               md5
```

**Critical rule**: PostgreSQL reads `pg_hba.conf` **top to bottom** and stops at the first match. Put specific rules before broad ones.

| Rule Position | Type | Database | User | Source Address | Method | Priority |
|--------------|------|----------|------|---------------|--------|----------|
| Line 1 | host | all | all | 127.0.0.1/32 | scram-sha-256 | Highest |
| Line 2 | host | all | all | 192.168.1.0/24 | md5 | Medium |
| Line 3 | host | all | all | 0.0.0.0/0 | reject | Lowest |

No restart needed—just reload:

```bash
pg_ctl reload
# Or from SQL
SELECT pg_reload_conf();
```

### Step 4: The Firewall—This One Bit Me Three Times

You think everything's configured correctly. But there's a silent packet dropper in the middle.

```bash
# iptables
iptables -L -n | grep 5432

# firewalld
firewall-cmd --list-all

# ufw
ufw status

# For cloud VPS—check security group rules too
```

Open the port:

```bash
# firewalld
firewall-cmd --permanent --add-port=5432/tcp
firewall-cmd --reload

# ufw
ufw allow 5432/tcp

# iptables
iptables -A INPUT -p tcp --dport 5432 -j ACCEPT
```

### Step 5: The Definitive Test

```bash
# Raw TCP test
telnet 192.168.1.100 5432

# Or with nc
nc -zv 192.168.1.100 5432
```

If `telnet` connects but `psql` still fails, **now** you have a `pg_hba.conf` or authentication problem. If `telnet` fails, it's still a network/firewall/service issue.

## Real-World War Stories

### Docker Deployment Gotchas

```bash
# Container's running, but host can't connect?
# Check port mapping
docker ps | grep postgres

# Proper way
docker run -d \
  -p 5432:5432 \
  -e POSTGRES_PASSWORD=mysecret \
  postgres:15
```

Pro tip: If you're running multiple PostgreSQL instances on the same host, Docker's port mapping can mask which container is actually listening.

### Cloud Provider Double Firewall

AWS, GCP, Azure—they all have **two layers** of network filtering. The instance-level firewall (iptables/ufw) AND the cloud security group. I've debugged for an hour only to find the security group inbound rule was missing. Check both.

### IPv6 vs IPv4 Trap

PostgreSQL might listen on `[::]:5432` (IPv6) but your client tries `127.0.0.1` (IPv4). Check:

```bash
ss -tlnp | grep 5432
```

If you only see `[::]:5432` but not `0.0.0.0:5432`, force IPv4 in `postgresql.conf`:

```ini
listen_addresses = '0.0.0.0'
```

## FAQ

**Q: `systemctl status postgresql` shows running, but connection is still refused. Why?**

A: Most likely PostgreSQL is listening on `127.0.0.1` only. Run `ss -tlnp | grep 5432` to check the actual listening address. Another possibility: the `port` in `postgresql.conf` isn't 5432.

**Q: Do I need to restart PostgreSQL after changing `pg_hba.conf`?**

A: No. Use `pg_ctl reload` or `SELECT pg_reload_conf()`. Only `postgresql.conf` changes to `listen_addresses` or `port` require a full restart.

**Q: Firewall is open on port 5432, but I still can't connect. What's next?**

A: Check SELinux or AppArmor. On CentOS/RHEL, SELinux blocks PostgreSQL from listening on non-standard ports or connecting to remote databases. Run `ausearch -m avc` to check SELinux audit logs.

**Q: How do I tell if it's a firewall reject vs PostgreSQL reject?**

A: Use `telnet`. If `telnet` returns "Connection refused", it's firewall or no service. If `telnet` connects but `psql` says "no pg_hba.conf entry", it's an authentication config issue.

**Q: Any special considerations for Kubernetes PostgreSQL deployments?**

A: Check the Service's `targetPort` matches the container port. Verify the Pod's `readinessProbe` config. For StatefulSets, Pod IPs change on restart—use a Headless Service with DNS-based discovery.

## Bottom Line

In my experience, 80% of PostgreSQL connection refused issues are config oversights, 15% are firewall misconfiguration, and maybe 5% are actual bugs. Follow this checklist in order, and you'll have it sorted in under ten minutes. Don't start by reinstalling—I've seen someone do that three times before realizing `listen_addresses` was the culprit.

If this hits production, fail over to your replica first. Debug the primary offline. Your users don't care about your troubleshooting process—they just want the database to work.
