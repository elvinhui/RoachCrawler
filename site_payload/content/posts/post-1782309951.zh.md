## 别再迷信单一大模型了

过去半年，我团队一直在跟“模型选型”这个老问题死磕。每次新项目启动，总要纠结：是咬牙上 Claude Fable 5 烧钱，还是用 GPT-5.5 凑合？结果呢？Fable 贵得离谱，GPT 在某些推理场景又拉胯。

直到上个月，我在 Reddit 上看到有人讨论 OpenRouter 的 Fusion API。当时那条帖子的标题很扎眼：“OpenRouter Fusion API Gets Near Fable 5 Results For Less”。我第一反应是——又来了，营销号吹牛。但点进去一看，评论区有几个老哥贴了实测数据，说用一组便宜模型组合 + 一个“法官”模型做汇总，效果居然真能跟 Fable 5 掰手腕。

我决定亲自踩坑。

## Fusion 到底是个啥？

简单说，Fusion 不是让你调用一个模型，而是让你定义一个“模型陪审团”。你发一个 prompt 过去，OpenRouter 会同时把它发给多个模型（比如 GPT-5.5、DeepSeek V4 Pro、Gemini 3 Flash），然后一个“法官”模型（Judge Model）把这些答案揉在一起，去芜存菁，输出最终结果。

这玩意儿本质上是一种 MoE（混合专家）的 API 化实现。但跟传统 MoE 不同的是，你不用自己去搭建路由、聚合、去重那一套基础设施——OpenRouter 全给你包了。

## 我踩的坑和真香时刻

### 坑 1：配置文档写得太烂

OpenRouter 官方的 Fusion 文档，说实话，信息密度极低。我花了半小时才搞清楚怎么在请求体里定义 panel。关键字段是 `models` 和 `judge`，但示例代码里居然没写清楚 judge 模型怎么传参数。

最后我是翻 GitHub 上一个 demo 才搞明白的：

```python
import openai

client = openai.OpenAI(
    base_url="https://openrouter.ai/api/v1",
    api_key="sk-your-key-here"
)

response = client.chat.completions.create(
    model="openrouter/fusion",
    messages=[
        {"role": "user", "content": "解释一下量子纠缠的物理原理，用通俗的语言"}
    ],
    extra_body={
        "fusion": {
            "models": [
                "openai/gpt-5.5",
                "anthropic/claude-opus-4.8",
                "google/gemini-3-flash"
            ],
            "judge": {
                "model": "anthropic/claude-opus-latest",
                "params": {
                    "temperature": 0.3,
                    "max_tokens": 2048
                }
            }
        }
    }
)

print(response.choices[0].message.content)
```

**注意**：`model` 字段必须设为 `"openrouter/fusion"`，然后在 `extra_body` 里定义 panel。我一开始以为要直接传模型名列表，结果 API 返回 400——这坑我替你们踩了。

### 坑 2：法官模型选不对，结果反而更差

我试过用 GPT-5.5 当法官，结果它把几个模型的答案简单拼凑了一下，输出了一堆废话。后来换成 Claude Opus 4.8 当法官，效果明显提升。Reddit 上有人推荐用 `~anthropic/claude-opus-latest`（带波浪号的版本会自动追踪最新版），我实测下来确实稳。

### 真香：成本确实降了

我们拿一个内部的知识库问答任务做了对比测试：

| 方案 | 单次请求成本 | P99 延迟 | 准确率（人工评估） |
|---|---|---|---|
| Claude Fable 5 单模型 | $0.085 | 4.2s | 89% |
| GPT-5.5 单模型 | $0.032 | 1.8s | 76% |
| Fusion（GPT-5.5 + DeepSeek V4 Pro + Gemini 3 Flash，法官用 Claude Opus） | $0.048 | 3.1s | 87% |

准确率只比 Fable 5 低了 2 个百分点，但成本下降接近一半。对于不需要 100% 精度的场景（比如内容摘要、初稿生成），这个性价比非常香。

## 什么时候该用 Fusion？

我个人的经验法则：

- **复杂推理任务**（法律分析、代码审查、数学证明）→ 用 Fusion，多个模型交叉验证能显著减少幻觉
- **创意生成任务**（文案、故事、营销方案）→ 单模型就够了，Fusion 反而可能抹平创意多样性
- **实时对话**（聊天机器人、客服）→ 别用 Fusion，3 秒延迟用户等不了
- **高精度需求**（医疗诊断、金融合规）→ 还是上 Fable 5 吧，Fusion 的 87% 准确率不够用

## 社区在吵什么？

Reddit 上最近有个帖子热度很高：“OpenRouter Fusion API Makes Claude Fable 5 Look Outdated”。评论区吵得不可开交。支持派认为 Fusion 代表了“模型民主化”的趋势——不再被单一供应商锁定。反对派则指出，Fusion 的延迟问题在 production 环境下是致命伤。

我的观点？Fusion 不是 Fable 5 的替代品，而是对它的补充。聪明的做法是：在路由层做动态决策——简单问题走单模型，复杂问题走 Fusion。我们正在内部搞这个 routing layer，等稳定了再写一篇分享。

## 常见问题

### Fusion 支持哪些模型？

目前支持 OpenAI、Anthropic、Google、DeepSeek、Kimi 等主流厂商的 400+ 模型。具体列表看 OpenRouter 官网。

### 法官模型可以自定义吗？

可以。你可以在 `judge` 参数里指定任意受支持的模型。建议用推理能力强的模型（Claude Opus、GPT-5.5）当法官。

### Fusion 的延迟大概多少？

取决于你选的模型组合。轻量组合（GPT-5.5 + Gemini 3 Flash）大约 2-3 秒，重量组合（加上 Claude Opus 当法官）可能到 4-5 秒。比单模型慢，但比串行调用多个模型快。

### 成本怎么算？

按所有参与模型的输出 token 总和计费。法官模型的输出也算。OpenRouter 官网有价格计算器。
