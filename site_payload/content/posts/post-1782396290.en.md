## The Moment You Realize curl Isn't There

Last week, one of our production containers blew up. The image had no curl, no wget, not even Python. Our ops guy was panicking — "I can't even run a health check!"

Relax. Bash has been hiding a Swiss Army knife all along: `/dev/tcp`.

This isn't new. It's Plan 9's legacy — Bash has been quietly mimicking the `/net` interface for years. And guess what? You can hand-craft HTTP requests with it.

## The Basics: GET in Three Lines

Here's the simplest version:

```bash
exec 3<>/dev/tcp/example.com/80
echo -e "GET / HTTP/1.1\r\nHost: example.com\r\nConnection: close\r\n\r\n" >&3
cat <&3
```

`exec 3<>` opens a bidirectional file descriptor to example.com:80. Then we manually craft an HTTP/1.1 GET request and read the response back.

No curl. No wget. No Python. Pure Bash.

## Level Up: A Reusable Function

Typing that raw every time gets old. Wrap it:

```bash
http_get() {
    local host=$1 path=${2:-/} port=${3:-80}
    exec 3<>/dev/tcp/$host/$port
    echo -e "GET $path HTTP/1.1\r\nHost: $host\r\nConnection: close\r\n\r\n" >&3
    cat <&3
    exec 3>&-
}
```

Usage: `http_get example.com /api/health`

## Real Talk: A Health Check Script

Here's something I actually used in a Kubernetes initContainer:

```bash
#!/bin/bash
check_service() {
    local host=$1 port=$2
    exec 3<>/dev/tcp/$host/$port 2>/dev/null || return 1
    echo -e "GET /health HTTP/1.1\r\nHost: $host\r\nConnection: close\r\n\r\n" >&3
    local response=$(head -1 <&3)
    exec 3>&-
    [[ "$response" == *"200"* ]]
}

# Wait for MySQL
for i in {1..30}; do
    if check_service mysql 3306; then
        echo "MySQL is ready"
        break
    fi
    sleep 2
done
```

Shaved about 20MB off our image size. Worth it.

## But Here's Where It Gets Ugly

Don't get too excited. `/dev/tcp` has some serious gotchas:

1. **HTTP only**. Forget HTTPS — you can't do TLS handshake in Bash.

2. **Compile-time option**. Not every system ships with it. Check:
   ```bash
   [ -r /dev/tcp ] && echo "supported" || echo "not supported"
   ```

3. **Performance is garbage**. Every request opens a new TCP connection. No keep-alive. Don't even think about load testing.

4. **Chunked encoding will ruin your day**. Some servers return chunked responses and your `cat` will hang forever. Workaround:
   ```bash
   cat <&3 | head -c $(grep -o 'Content-Length: [0-9]*' | cut -d' ' -f2)
   ```

## The Comparison: curl vs /dev/tcp

| Feature | curl | /dev/tcp |
|---------|------|----------|
| HTTPS | ✅ Native | ❌ Nope |
| HTTP/2 | ✅ Supported | ❌ HTTP/1.1 only |
| Connection reuse | ✅ Connection pool | ❌ New connection each time |
| Image footprint | ~20MB | 0 (built into Bash) |
| Performance | High | Low |
| Script-friendly | Needs install | Zero-dependency |
| Error handling | Detailed | Barebones |
| Debugging | -v, --trace | Manual echo |

## When to Use It

- Docker images without curl (and you're optimizing for size)
- Embedded systems where every kilobyte counts
- Ad-hoc debugging when you have nothing else
- Quick port availability checks

## When to Avoid It

- HTTPS endpoints (just install curl or wget)
- Production monitoring scripts (use proper health checks)
- Any scenario with complex response handling

## FAQ

**Q: Does /dev/tcp support HTTPS?**
A: No. `/dev/tcp` only handles the TCP layer. TLS handshake requires logic Bash can't do.

**Q: Does every Linux distro support it?**
A: Not necessarily. Bash needs the `--enable-net-redirections` compile flag. Most mainstream distros have it enabled, but Alpine Linux uses ash by default — no dice.

**Q: How's the performance?**
A: Poor. Each request opens a new TCP connection with no keep-alive. Fine for occasional checks, terrible for high throughput.

**Q: How do I read response headers?**
A: Use `read -u 3 line` in a loop. An empty line marks the end of headers.

**Q: Can I send POST requests?**
A: Yes — just craft the HTTP request manually. But get the Content-Length right or you'll hang the connection.
